# 独立钱包扩展到 BTC 与闪电网络方案

这份文档不是“功能愿景”，而是给以后真正要开工的人看的实施路线。

结论先写在前面：

- 现在这套独立钱包不适合直接硬加闪电网络。
- 最稳的路线是先补 `BTC` 链上能力，再把闪电网络做成单独在线模块。
- `BTC` 链上可以复用现有 `Satochip` 卡和树莓派签名链。
- 闪电网络不建议复用当前“空气隔离二维码签名”主流程，而是应该连接外部节点或服务。

## 1. 当前项目现状

独立钱包当前定位：

- `Arbitrum One` 观察钱包
- 手机里不保存私钥
- 树莓派负责离线签名
- `Satochip` 卡负责密钥和签名
- 重点服务 `Hyperliquid` 和 `WalletConnect`

现在这条链路是明显的 `EVM` 架构：

- 安卓钱包链配置只有 `Arbitrum One`
- 安卓钱包 RPC 全是 `eth_*`
- 二维码请求协议写死为 `ArbitrumWallet`
- 树莓派签名器默认路径是 `m/44'/60'/0'/0/0`
- 树莓派签名逻辑只处理 `EVM transaction / personal_sign / typed data`
- `WalletConnect` 只暴露 `eip155`

但底层硬件并不是没有 `BTC` 能力：

- `Satochip` 卡本身支持 `Bitcoin transaction` 和 `Bitcoin message` 签名
- 卡固件支持标准交易和 `SegWit` 解析
- `satochip-lib` 已经能导出 `xpub / ypub / zpub`

所以真正缺的不是卡，而是：

- 安卓端没有 `BTC` 观察钱包逻辑
- 安卓端没有 `UTXO / 地址派生 / PSBT` 处理
- 树莓派端没有 `BTC/PSBT` 请求协议和签名流程
- 当前二维码协议完全围绕 `EVM`
- 闪电网络要求在线状态，不适合直接套用当前离线签名主流程

## 2. 为什么不能直接给当前钱包硬加闪电网络

闪电网络和你现在这套项目的核心假设不一样。

当前项目依赖：

- 观察钱包在手机上准备请求
- 请求通过二维码发给树莓派
- 树莓派用卡离线签名
- 手机扫回签名结果再广播

而闪电网络天然依赖：

- 节点持续在线
- 通道状态实时同步
- 付款路由和失败重试
- 发票状态更新
- 部分场景需要热签名或半热签名

这会带来两个冲突：

- 当前树莓派签名链是“离线批处理”，闪电更像“在线会话”
- 当前协议是“单次签名请求”，闪电经常需要节点级状态机

所以如果直接在当前 `Arbitrum` 钱包里塞一个“闪电”按钮，最后维护会很痛，问题会集中在：

- 架构混乱
- 协议混杂
- 回归测试爆炸
- 用户心智混乱

## 3. 推荐路线

### 路线 A：先做 BTC 链上

这是最推荐、也最顺着现有项目能力的一步。

目标：

- 安卓钱包能导入并显示 `BTC` 观察地址
- 手机能派生接收地址和找零地址
- 手机能看 `UTXO`、余额、历史
- 手机能构造 `PSBT`
- 树莓派能读取 `PSBT` 并用 `Satochip` 卡签名
- 手机能接收签名后的结果并广播

理由：

- 现有卡和底层库已经有 `BTC` 能力
- 这一步可以最大化复用硬件和安全模型
- 做完以后，整个项目会从“只会 EVM”升级成“EVM + BTC 链上”

### 路线 B：再做闪电网络在线模块

目标：

- 手机端支持 `BOLT11`
- 支持收款发票展示
- 支持付款请求解析
- 支持 `LNURL-pay / LNURL-withdraw` 基础流程
- 后端连接外部闪电节点或服务

推荐方式：

- 安卓端只做 UI、支付入口、状态展示
- 实际闪电能力接外部节点
- 节点可以是你自己的，也可以是你控制的轻量服务层

不推荐一开始就做：

- 在手机端内嵌完整闪电节点
- 强行把闪电签名也塞进树莓派二维码主流程

### 路线 C：最后再统一界面

等 `BTC` 链上和闪电都稳定以后，再决定是否把它们继续放在同一个安卓 App 里。

推荐的最终 UI 结构：

- `Arbitrum`
- `Bitcoin`
- `Lightning`

每个入口都用不同的签名和联网模型，不要伪装成“一个完全相同的账户体系”。

## 4. 技术方案建议

### 4.1 BTC 链上协议

推荐用 `PSBT`，不要自己发明原始交易签名协议。

原因：

- `PSBT` 是标准格式
- 便于调试和兼容
- 后续如果要支持多输入、多找零、硬件签名，会省很多事

二维码建议：

- 第一阶段可以沿用现在的 `tp:multiFragment` 分片框架
- 但请求内容不要再叫 `ArbitrumWallet`
- 建议新建 `protocol=BitcoinWallet`
- 动作建议至少区分：
  - `getXpub`
  - `signPsbt`
  - `signMessage`

### 4.2 BTC 观察钱包数据源

安卓端需要补：

- 地址派生
- `UTXO` 查询
- 余额查询
- 交易历史
- 广播接口

优先建议：

- 先接单一数据源抽象层
- 上层 UI 只依赖统一接口
- 后面再决定底层实际走哪种 `API / Electrum / 自建服务`

不要一开始就把数据源写死进 UI。

### 4.3 闪电网络形态

推荐做成“安卓前端 + 外部闪电节点”。

建议功能边界：

- 安卓端保存节点连接配置
- 安卓端负责发票扫码、付款确认、状态展示
- 节点负责路由、余额、付款执行、发票状态

这样做的好处：

- 不破坏当前离线签名模型
- 失败场景更容易定位
- 以后节点换实现，手机端 UI 不用推翻重来

## 5. 具体改动位置

### 5.1 安卓独立钱包 `wallet/`

第一阶段要新增或改造的模块：

- `ArbitrumConfig.kt`
  需要抽象成更通用的链定义，不再只服务 `EVM`
- `ArbitrumRpc.kt`
  不能继续承担所有链逻辑，建议拆成 `EvmRpc.kt`，另加 `BitcoinRpc.kt` 或 `BitcoinDataSource.kt`
- `WalletModels.kt`
  要增加 `BTC` 账户、地址类型、`UTXO`、交易历史模型
- `WalletStorage.kt`
  需要保存 `BTC` 观察账户配置、派生索引、节点配置
- `MainViewModel.kt`
  需要把“发起请求”从 `EVM-only` 改成按链路由
- `MainActivity.kt`
  需要增加 `Bitcoin` 和未来 `Lightning` 的独立页面
- `TpRequestBuilder.kt`
  不能再只生成 `ArbitrumWallet` 请求，需要拆成协议构建器接口

建议新增的文件方向：

- `BitcoinAccount.kt`
- `BitcoinDerivation.kt`
- `BitcoinAddressCodec.kt`
- `BitcoinDataSource.kt`
- `PsbtQrCodec.kt`
- `LightningModels.kt`
- `LightningService.kt`

### 5.2 树莓派签名端 `pi-signer/`

第一阶段需要新增：

- `Bitcoin` 请求解析
- `PSBT` 签名入口
- `xpub` 导出命令
- `BTC message` 签名入口

建议改动方向：

- `PiMain.kt`
  命令行增加 `get-xpub`、`sign-psbt`
- `SatochipSigner.kt`
  增加 `BTC` 派生和签名分支，不要继续只返回以太坊地址
- `TpQrCodec.kt`
  增加 `BitcoinWallet` 协议解析
- 新增 `PsbtSigner.kt`
  专门处理 `PSBT`

### 5.3 树莓派固件 `seedsigner-os/`

固件层不一定要大改协议，但要确认：

- 运行时依赖里是否已有足够的 `BTC` 处理库
- 新增 `PSBT` 解析库后镜像大小是否还可接受
- 二维码容量和扫描速度是否还能用

建议：

- 先在 `pi-signer` 单独原型验证
- 验通后再收进树莓派固件快照

### 5.4 智能卡与底层库

这部分优先复用，不要乱改卡固件。

优先复用：

- `card-applet`
  现有 `Bitcoin/SegWit` 解析能力
- `satochip-lib`
  现有 `xpub/zpub` 导出能力

只有当现有接口无法满足 `PSBT` 签名路径时，再考虑扩卡侧命令。

## 6. 实施顺序

### 第 1 步：做 BTC 观察账户只读版

目标：

- 手机能导入 `zpub`
- 能显示地址、余额、历史
- 先不做签名

完成标志：

- 安卓端能稳定显示 `BTC` 观察账户

### 第 2 步：做 BTC 请求二维码与树莓派签名

目标：

- 安卓端构造 `PSBT`
- 二维码发送到树莓派
- 树莓派调用卡完成签名
- 安卓端扫回签名结果并广播

完成标志：

- 能从手机发起一笔真实 `BTC` 转账并完成广播

### 第 3 步：做 BTC 用户界面和维护文档

目标：

- 完善地址管理
- 完善手续费显示
- 完善找零说明
- 补使用教程和回归清单

### 第 4 步：做闪电网络最小可用版

目标：

- 扫 `BOLT11`
- 展示 invoice 内容
- 调外部节点完成支付
- 展示支付结果

完成标志：

- 可以完成最小的支付和收款演示

## 7. 工作量预估

如果只做 `BTC` 链上：

- 属于“中等偏大”改造
- 但仍在当前项目可控范围内

如果做 `BTC + 闪电` 一起上：

- 属于“大改造”
- 不建议一次性铺开

如果想把闪电做成成熟可长期维护的模块：

- 更接近一个新产品线，而不是“加个功能”

## 8. 最容易踩坑的地方

- 把 `BTC` 链上和闪电网络混成同一种请求协议
- 继续沿用 `ArbitrumWallet` 命名导致后面协议越来越乱
- 让树莓派去承担闪电节点职责
- 在安卓 UI 层写死某个 `BTC API`
- 没有先做 `xpub/zpub` 只读验证，就直接做签名
- 没有把 `BTC` 回归测试单独列出来

## 9. 推荐的决策

如果以后真的要开工，我建议只做下面这个版本：

1. 先做 `BTC` 链上观察 + `PSBT` 签名。
2. 树莓派和卡只负责 `BTC` 链上签名，不碰闪电。
3. 闪电网络单独做成在线模块，连接外部节点。
4. 等 `BTC` 链上稳定以后，再决定闪电要不要并入同一个 App。

这是当前项目里风险最低、复用最高、长期维护也最稳的路径。

## 10. 开工前检查清单

- 先确认你要的是：
  - `BTC` 链上
  - 还是闪电网络
  - 还是两个都要
- 如果两个都要，先只排 `BTC` 链上
- 先做 `zpub` 导出原型
- 先做安卓端只读账户原型
- 原型稳定后再做 `PSBT`
- `PSBT` 跑通后再讨论闪电

如果以后正式开工，这份文档应配套再新增：

- `BTC` 使用教程
- `BTC` 回归测试清单
- `闪电网络` 节点配置说明
- `二维码协议` 文档
