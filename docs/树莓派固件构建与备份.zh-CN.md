# 树莓派固件构建与备份

这份文档按当前脚本和当前仓库产物重新整理，目标只有两个：

- 让你以后还能稳定重编
- 让源码、镜像、`sha256`、`build-info` 尽量继续对得上

## 1. 当前固定入口

正式构建：

```bash
bash scripts/build_pi_firmware_from_snapshot.sh
bash scripts/check_release_artifacts.sh
```

不要优先直接裸跑：

```bash
seedsigner-os/opt/build.sh
```

因为根目录脚本已经做了当前项目最需要的保护和打包动作。

## 2. 当前脚本做了什么

### `scripts/run_seedsigner_build.sh`

负责：

- 把仓库挂到纯英文构建根目录
- 清掉运行时 `__pycache__`
- 同步翻译资源和默认设置
- 用低优先级跑 `./build.sh --pi0 --smartcard --skip-repo`

默认负载控制：

- `BR2_JLEVEL=4`
- `taskset 0,1,2,3`
- `nice 19`
- `ionice -c3`

默认正式模式：

- `TP_BUILD_CLEAN_MODE=clean`

### `scripts/build_pi_firmware_from_snapshot.sh`

负责：

- 调用上面的 build 脚本
- 找到原始镜像
- 压缩成仓库里的目标镜像
- 生成 `.sha256`
- 生成 `.build-info.txt`

如果你要覆盖：

- `dist/system-update-latest.img.xz`

当前脚本会额外要求：

- 仓库必须是干净的
- 构建模式必须是 `clean`

### `scripts/check_release_artifacts.sh`

负责检查：

- 镜像与 `.sha256` 是否一致
- `.build-info.txt` 是否与镜像内容一致
- `system-update-latest` 是否保持 clean 基线约束
- `repair7` 这类功能备份包的 `sha256/build-info` 是否自洽
- `repo_head` 是否是当前仓库可达提交

补充说明：

- 当前仓库里的 `system-update-latest.build-info.txt` 还是历史格式，缺少 `build_clean_mode`
- 现在脚本会对它给出 `legacy clean-baseline metadata` 警告，但不会误判镜像损坏
- 下一次真正用 `clean` 流程重打 `system-update-latest` 时，这个字段应该补齐

## 3. 当前最重要的输入

树莓派固件现在最关键的固定输入不是“某个上游分支”，而是仓库里这两块：

- `seedsigner-os/opt/rootfs-overlay/opt/`
- `seedsigner-os/opt/external-packages/nfc-bindings/nfc-bindings.mk`

## 5. clean 包和测试包怎么区分

### 正式 clean 包

```bash
bash scripts/build_pi_firmware_from_snapshot.sh
bash scripts/check_release_artifacts.sh
```

目标通常是：

- `dist/system-update-latest.img.xz`

### 测试包

```bash
TP_BUILD_CLEAN_MODE=no-clean \
DIST_IMG=dist/system-update-test.img.xz \
DIST_SUM=dist/system-update-test.img.xz.sha256 \
DIST_INFO=dist/system-update-test.build-info.txt \
bash scripts/build_pi_firmware_from_snapshot.sh
```

测试包可以快一些，但不要拿来冒充正式稳定版。

## 6. `build-info` 里最该看什么

至少看这些字段：

- `repo_head`
- `repo_dirty`
- `raw_image_sha256`
- `compressed_image_sha256`
- `runtime_snapshot_tree_sha256`
- `build_clean_mode`
  这是新格式 clean 基线最重要的字段之一；当前历史 `system-update-latest` 还没有这一行

当前 `system-update-latest.build-info.txt` 里最关键的基线值：

- `repo_head=f4f75ec85a7d4491b5ef16cda725899b8671a13e`
- `repo_dirty=0`
- `compressed_image_sha256=50d633dc207f6a0c80adeb2b551851cb0610df5c16f21bfde67075303a077982`
- `build_clean_mode`
  当前这张历史 clean 基线还没有写入；下次 clean 重打后必须补齐

当前 `repair7` 备份包则是：

- `repo_dirty=1`
- `build_clean_mode=no-clean`

所以它是“已验证能用的功能包”，不是新的 clean 稳定基线。

## 7. 当前两张镜像怎么管理

### `system-update-latest`

定位：

- 历史 clean 稳定备份
- 做复现与校验基线用

### `system-update-offline-signer-repair7`

定位：

- 当前已验证功能版
- 追溯源码时必须看 `offline-signer-repair7-source-20260330`

详细映射看：

- [固件与源码对应关系](固件与源码对应关系.zh-CN.md)

## 8. 推送 GitHub 前的顺序

推荐固定流程：

1. 先把源码和文档提交成干净 commit
2. 在这个 commit 上跑正式构建
3. 跑 `bash scripts/check_release_artifacts.sh`
4. 检查 `build-info`
5. 再单独提交 `dist/` 里的镜像、`.sha256`、`.build-info.txt`
6. 最后推 GitHub 和 Release

原因：

- `build-info` 里的 `repo_head` 表示“哪份源码产出了这张镜像”
- 镜像再回填到仓库后，仓库提交号会继续变化
- 所以源码提交和产物提交本来就应该分开看

## 9. 下次最容易犯错的地方

- 不要直接拿当前 `main` 去猜 `repair7` 对应源码
- 不要用 `no-clean` 覆盖 `system-update-latest`
- 不要忘记一起保留 `.sha256` 和 `.build-info.txt`
- 不要只留 `output/` 里的原始镜像，不回填 `dist/`
