# 树莓派固件构建与备份

这份文档只讲一件事：

- 怎么从当前仓库重新编出可用的树莓派固件
- 怎么把当前可用固件稳定备份到仓库和 GitHub

如果以后只改树莓派固件，优先先看这篇。

## 1. 当前已经验证可用的关键输入

当前可用固件不是只靠 `seedsigner-os` 上游源码就能重现。

真正必须固定的是：

- `seedsigner-os/opt/rootfs-overlay/opt/`
- `seedsigner-os/opt/external-packages/nfc-bindings/nfc-bindings.mk`

其中当前已经验证可用的运行时快照时间是：

```text
seedsigner-os/opt/rootfs-overlay/opt/src/.build_commit_time = 2026-03-10 16:30
```

如果以后这个目录丢了、被 `.gitignore` 忽略了，或者又回到“构建时临时拉外部 `dev` 分支”的方式，就很容易出现：

- 能编过
- 但镜像和原来不一样
- 屏幕不亮
- 键位不对

## 2. 以后只用这一条命令

标准命令：

```bash
bash scripts/build_pi_firmware_from_snapshot.sh
```

这个脚本会按顺序做完：

1. 调用 `scripts/run_seedsigner_build.sh`
2. 用当前仓库里已经冻结的 `rootfs-overlay/opt` 快照构建
3. 生成原始镜像：
   `seedsigner-os/images/seedsigner_os.dev_.pi0-smartcard.img`
4. 自动压缩并覆盖仓库里的稳定备份：
   `dist/system-update-latest.img.xz`
5. 自动更新：
   - `dist/system-update-latest.img.xz.sha256`
   - `dist/system-update-latest.build-info.txt`

这条默认命令现在还有一个保护：

- 如果仓库不是干净状态，脚本会拒绝覆盖 `dist/system-update-latest.*`
- 想做测试包，就显式换成别的文件名，例如：

```bash
DIST_IMG=dist/system-update-bluewallet-test.img.xz \
DIST_SUM=dist/system-update-bluewallet-test.img.xz.sha256 \
DIST_INFO=dist/system-update-bluewallet-test.build-info.txt \
bash scripts/build_pi_firmware_from_snapshot.sh
```

## 3. 这套脚本为什么更稳

`scripts/run_seedsigner_build.sh` 已经固定为：

- `--skip-repo`
- `--no-clean`
- `BR2_JLEVEL=4`
- `taskset -c 0,1,2,3`
- `nice 19`
- `ionice -c3`

这样做的目的有两个：

1. 不再从外部仓库临时拉最新代码，避免“今天能编、明天不一样”。
2. 不再像之前那样一上来把整台电脑顶满，降低卡死概率。

如果你确实要改并发，可以自己设环境变量：

```bash
BR2_JLEVEL=3 TP_BUILD_CPUSET=0,1,2 bash scripts/build_pi_firmware_from_snapshot.sh
```

## 4. 当前产物位置

构建完成后，重点看这几个文件：

- 原始镜像：
  `seedsigner-os/images/seedsigner_os.dev_.pi0-smartcard.img`
- 仓库稳定备份：
  `dist/system-update-latest.img.xz`
- 压缩镜像校验：
  `dist/system-update-latest.img.xz.sha256`
- 构建信息：
  `dist/system-update-latest.build-info.txt`

`build-info` 里会记录：

- 运行时快照时间
- 原始镜像 `sha256`
- 压缩镜像 `sha256`
- 用的脚本名
- 打包时间

## 5. 看进度怎么做

构建日志：

```bash
tail -f logs/seedsigner-build-live.log
```

如果想看系统整体情况：

```bash
watch -n 1 'uptime; echo; free -h; echo; pgrep -af "build.sh --pi0 --smartcard --skip-repo --no-clean|linux-custom|post-image-tpminimal|zImage"'
```

## 6. 推 GitHub 前的最短顺序

每次树莓派固件改完后，照这个顺序走：

1. 先把源码和文档提交成一个干净 commit。
2. 在这个干净 commit 上跑：
   `bash scripts/build_pi_firmware_from_snapshot.sh`
3. 确认：
   - 镜像能亮屏
   - 关键按键没问题
4. 跑：
   `bash scripts/check_release_artifacts.sh`
5. 检查 `dist/system-update-latest.build-info.txt`，至少确认：
   - `repo_head` 是刚才那个源码 commit
   - `repo_dirty=0`
   - `compressed_image_sha256` 和 `.sha256` 一致
6. 再单独提交：
   - `dist/system-update-latest.img.xz`
   - `dist/system-update-latest.img.xz.sha256`
   - `dist/system-update-latest.build-info.txt`
7. 推 GitHub 时，把源码 commit 和 `dist/` 提交一起推上去。
8. 建 GitHub Release 时，以 `build-info` 里的 `repo_head` 对应 commit 或 tag 作为源码基准，再上传这 3 个 `dist` 文件。

为什么要分成“源码 commit”和“dist 提交”两步：

- 因为 `build-info` 里会记录源码 commit
- 但镜像文件本身又要被回填进仓库
- 如果把镜像文件也算进同一个源码 commit，提交哈希会再次变化，永远对不上

所以以后要认准：

- `build-info` 的 `repo_head` 代表“这张固件是由哪份源码编出来的”
- `dist/` 的后续提交只是把这张已经验证过的固件备份进仓库

## 7. 以后最容易犯错的地方

不要再走这几条旧路：

- 不要直接裸跑 `seedsigner-os/opt/build.sh`
  原因：默认会去拉外部仓库的 `dev`
- 不要再让 `rootfs-overlay/opt` 被忽略
  原因：它就是当前真正可用固件的运行时输入
- 不要只留 `output/` 里的临时镜像
  原因：`output/` 是构建缓存，不是长期备份
- 不要只改代码不更新 `dist` 和 `sha256`
  原因：以后回看时根本不知道哪张是验证通过的
