# 树莓派固件构建与备份

这份文档按当前脚本和当前仓库产物重新整理，目标只有两个：

- 让你以后还能稳定重编
- 让源码、镜像、`sha256`、`build-info` 尽量继续对得上

## 1. 当前固定入口

正式构建：

```bash
bash scripts/build_pi_firmware_from_snapshot.sh
bash scripts/check_release_artifacts.sh
```

不要优先直接裸跑：

```bash
seedsigner-os/opt/build.sh
```

因为根目录脚本已经做了当前项目最需要的保护和打包动作。

## 2. 当前脚本做了什么

### `scripts/run_seedsigner_build.sh`

负责：

- 把仓库挂到纯英文构建根目录
- 清掉运行时 `__pycache__`
- 同步翻译资源和默认设置
- 用低优先级跑 `./build.sh --pi0 --smartcard --skip-repo`

默认负载控制：

- `BR2_JLEVEL=4`
- `taskset 0,1,2,3`
- `nice 19`
- `ionice -c3`

默认正式模式：

- `TP_BUILD_CLEAN_MODE=clean`
- 构建时会先复制一份临时 `rootfs-overlay`，再往副本里生成完整性清单
- 不会再把 `offline-signer-firmware-integrity.json` 直接回写到源码树里

### `scripts/build_pi_firmware_from_snapshot.sh`

负责：

- 调用上面的 build 脚本
- 找到原始镜像
- 压缩成仓库里的目标镜像
- 生成 `.sha256`
- 生成 `.build-info.txt`

如果你要覆盖：

- `dist/system-update-latest.img.xz`

当前脚本会额外要求：

- 仓库必须是干净的
- 构建模式必须是 `clean`
- `build-info` 里的构建时间固定取源码提交时间，避免每次只因为“当前时刻不同”就写出不同元数据

如果你只是要当前工作区测试包，不要直接拿它覆盖 `system-update-latest.*`。
统一改用：

```bash
bash scripts/build_current_firmware.sh
```

它默认输出：

- `dist/system-update-worktree-latest.img.xz`
- `dist/system-update-worktree-latest.img.xz.sha256`
- `dist/system-update-worktree-latest.build-info.txt`

### `scripts/check_release_artifacts.sh`

负责检查：

- 镜像与 `.sha256` 是否一致
- `.build-info.txt` 是否与镜像内容一致
- `system-update-latest` 是否保持 clean 基线约束
- `review-pinless` 这类功能备份包的 `sha256/build-info` 是否自洽
- `repo_head` 是否是当前仓库可达提交

补充说明：

- `system-update-latest.build-info.txt` 只有在 clean `HEAD` 基线包场景下才应该满足 `repo_dirty=0` + `build_clean_mode=clean`
- `legacy clean-baseline metadata` 警告只留给更早的历史包

## 3. 当前最重要的输入

树莓派固件现在最关键的固定输入不是“某个上游分支”，而是仓库里这两块：

- `seedsigner-os/opt/rootfs-overlay/opt/`
- `seedsigner-os/opt/external-packages/nfc-bindings/nfc-bindings.mk`

补充：

- 运行时完整性清单 `offline-signer-firmware-integrity.json` 现在视为构建产物，不再作为源码快照的一部分参与版本冻结

运行时快照时间记录在：

- `seedsigner-os/opt/rootfs-overlay/opt/src/.build_commit_time`

当前值：

```text
2026-03-10 16:30
```

## 4. 当前产物位置

原始镜像默认在：

- `TP_ASCII_BASE/images/seedsigner_os.dev_.pi0-smartcard.img`

仓库当前保留的正式压缩镜像：

- `dist/system-update-latest.img.xz`
- 当前工作区测试镜像：
  `dist/system-update-worktree-latest.img.xz`

对应校验和构建记录：

- `.sha256`
- `.build-info.txt`

## 5. clean 包和测试包怎么区分

### 正式 clean 包

```bash
bash scripts/build_pi_firmware_from_snapshot.sh
bash scripts/check_release_artifacts.sh
```

目标通常是：

- `dist/system-update-latest.img.xz`

### 测试包

```bash
bash scripts/build_current_firmware.sh
```

测试包默认输出到 `system-update-worktree-latest.*`，不要再拿它冒充 clean 基线名。

## 6. `build-info` 里最该看什么

至少看这些字段：

- `repo_head`
- `repo_dirty`
- `raw_image_sha256`
- `compressed_image_sha256`
- `runtime_snapshot_tree_sha256`
- `build_clean_mode`
  这是当前 clean 正式包最重要的字段之一

当前 clean 基线最关键的是这组关系，而不是死记某一版旧哈希：

- `repo_dirty=0`
- `build_clean_mode=clean`
- `repo_head` 必须和你要的 `HEAD` / `source_tag` 对得上
- `compressed_image_sha256` 必须和 `.sha256` 文件一致

## 7. 当前正式镜像怎么管理

### `system-update-latest`

定位：

- 当前 clean 正式基线
- 现在主要做复现与校验基线

### `system-update-worktree-latest`

定位：

- 当前工作区测试包
- 默认允许带未提交改动或 `no-clean`
- 方便真机回归，但不应该拿来冒充 clean 基线

## 8. 推送 GitHub 前的顺序

推荐固定流程：

1. 先把源码和文档提交成干净 commit
2. 在这个 commit 上跑正式构建
3. 跑 `bash scripts/check_release_artifacts.sh`
4. 检查 `build-info`
5. 再单独提交 `dist/` 里的镜像、`.sha256`、`.build-info.txt`
6. 最后推 GitHub 和 Release

原因：

- `build-info` 里的 `repo_head` 表示“哪份源码产出了这张镜像”
- 镜像再回填到仓库后，仓库提交号会继续变化
- 所以源码提交和产物提交本来就应该分开看

## 9. 下次最容易犯错的地方

- 不要直接拿当前 `main` 去猜当前推荐 clean 包对应源码
- 不要用 `no-clean` 覆盖 `system-update-latest`
- 不要忘记一起保留 `.sha256` 和 `.build-info.txt`
- 不要只留 `output/` 里的原始镜像，不回填 `dist/`

## 10. GitHub 现在能帮你兜住什么

为了避免以后本地电脑没了就不知道这张固件是不是还能对上，GitHub 侧现在至少应该检查仓库里这份正式固件的自洽性。

对应工作流：

- `.github/workflows/firmware-release-verify.yml`

它会在 GitHub 上直接执行：

```bash
bash scripts/check_named_release.sh firmware-clean
```

这一步能帮你确认：

- `dist/system-update-latest.img.xz`
- `dist/system-update-latest.img.xz.sha256`
- `dist/system-update-latest.build-info.txt`

三者互相对得上，并且 `repo_head`、`repo_dirty`、`build_clean_mode` 满足当前 clean 基线规则。

注意：

- 这条工作流现在是“验包”，不是 GitHub 上完整重建整张固件
- 真正完整重建固件，仍然优先用本地或以后单独准备的自建 runner
- 但至少仓库里保留的正式固件现在不再只是“放着没人验”
