# 版本时间线与发布入口

这页只回答 4 个问题：

- 现在 GitHub Releases 里哪几个入口是当前该用的
- 哪些包只是历史归档，不要误刷
- 固件二进制到底对应哪份源码 tag
- 以后发版时，名字和 tag 应该怎么理解

## 2. 树莓派固件为什么有两条线

### 功能验证线

- 代表包：
  `system-update-offline-signer-repair7.img.xz`
- 适合：
  你现在日常真机使用
- 特点：
  功能最新，已经实机验证
- 注意：
  它不是 clean 复现基线，`build-info` 里是 `repo_dirty=1`、`build_clean_mode=no-clean`

### clean 基线线

- 代表包：
  `system-update-latest.img.xz`
- 适合：
  以后做复现、验包、校验构建流程
- 特点：
  是历史 clean 基线
- 注意：
  这张包的 `build-info` 还是旧格式，不一定带 `build_clean_mode`

## 3. 历史包怎么识别

GitHub Releases 里，下面这些命名现在都视为历史归档：

- `Offline Signer Firmware 2026-03-18 (historical)`
- `Offline Signer Firmware 2026-03-24 (historical)`
- `Offline Signer Firmware 2026-03-27 (historical)`
- `Offline Signer Firmware 2026-03-27-2 (historical)`
- `Satochip Wallet Android 2026-03-18 (historical preview)`
- `Satochip Wallet Android 2026-03-28 (historical)`
- `Satochip Wallet Android 2026-03-28 21:12 (historical old signing key)`
- `Smartcard App Android 2026-03-16 (historical preview)`
- `Smartcard App Android 2026-03-18 19:56 (historical)`

这些包保留的意义主要是：

- 追溯当时的界面和功能
- 回滚排障
- 对照历史文档

不要默认把它们当成“当前推荐下载”。

## 4. 固件和源码怎么对应

最容易弄错的一点是：

- GitHub `main`
- 某张历史固件
- 某个 release tag

这三者经常不是同一个提交。

当前最重要的对应关系：

- `offline-signer-firmware-20260330-repair7`
  - 固件 release tag
  - 对应功能验证包
  - 精确源码看：
    `offline-signer-repair7-source-20260330`

- `pi-signer-firmware-20260329`
  - 固件 release tag
  - 也是它自己的源码基线 tag
  - 对应 clean 基线包

详细字段看：

- [固件与源码对应关系](固件与源码对应关系.zh-CN.md)

## 5. 下次该怎么选

### 想直接使用

- 先下：
  `offline-signer-firmware-20260330-repair7`

### 想做复现或长期基线保存

- 先看：
  `pi-signer-firmware-20260329`

### 想继续开发新功能

- 看：
  `main`
- 但不要把 `main` 直接当成任意历史二进制的精确来源

## 6. 以后看到这些名字时怎么理解

- `offline-signer-firmware-*`
  树莓派离线签名器固件 release
- `offline-signer-repair7-source-*`
  精确冻结源码 tag
- `smartcard-app-android-*`
  安卓“智能卡”App release
- `wallet-android-*`
  安卓观察钱包 release
- `j3r180-card-firmware-*`
  智能卡固件 release

如果以后又出了新固件，最稳的做法还是：

1. 先看 GitHub Releases
2. 再看这页确认它属于哪条线
3. 最后去看对应源码 tag，而不是直接猜 `main`
