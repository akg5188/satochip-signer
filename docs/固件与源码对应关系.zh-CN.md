# 固件与源码对应关系

这页只回答一个问题：当前几个固件入口到底各自对应哪份源码。

## 1. 当前仓库保留的固件基线

定位：

- 仓库 `dist/` 里当前默认保留的镜像
- 对应 GitHub Release：
  `current-head-clean`
- 这份基线不是“自动等于当前 `HEAD`”，而是以它自己的 `build-info` 为准

关键值：

- 镜像：
  `dist/system-update-latest.img.xz`
- 当前仓库保留基线对应源码提交：
  `979f58d3ad5cecdfec319e14681cde006c7073ab`
- 当前仓库保留基线对应 build 时间：
  `2026-04-19T04:12:54Z`
- 当前工作区最新入口：
  `bash scripts/build_current_firmware.sh`
- 当前工作区测试包名：
  `dist/system-update-worktree-latest.img.xz`

也就是说：

- 仓库里现在保留的这份 `system-update-latest.*`，对应的是 `979f58d3...` 那次构建
- 想要当前 `HEAD` 的 clean 固件，改用 `firmware-clean`
- 想要当前工作区最新，包括未提交改动，改用 `build_current_firmware.sh`
- `build_current_firmware.sh` 默认不再覆盖 `system-update-latest.*`，而是单独写 `system-update-worktree-latest.*`

对应文件：

- `dist/system-update-latest.img.xz`
- `dist/system-update-latest.img.xz.sha256`
- `dist/system-update-latest.build-info.txt`

## 2. 当前 `HEAD` clean 固件入口

如果你要的是“按当前源码重新生成新的 clean 正式基线”，入口是：

```bash
bash scripts/rebuild_official_release.sh firmware-clean
```

关键含义：

- 这条命令跟随当前 `HEAD`
- 它重建出来的新产物才应该再用 `check_named_release.sh firmware-clean` 去核对
- 它的目标是生成“新的 clean 基线”，不是解释仓库里已经保留的旧基线产物

## 3. 历史公开固件

如果你要追 GitHub 上公开发布过的 `20260410b` 正式固件，固定对应关系还是保留的：

- 固件 release tag：
  `offline-signer-firmware-20260410b-clean`
- 源码冻结 tag：
  `offline-signer-clean-source-20260410b`
- 源码冻结提交：
  `281d45bfddb9b9150f48c840fafb3aa63aa624fb`
- 历史重建入口：
  `bash scripts/rebuild_official_release.sh firmware-public-20260410b-clean`

这份冻结里包含：

- 小屏 UI 排版收口，长内容优先改成摇杆上下滚动
- 签名完成后先显示摘要，再决定是否显示二维码
- 写卡后自动回读核验，覆盖指纹、`xpub / zpub`、首个地址和测试签名
- `查看助记词` 底部滚动留白修复
- `拍照创建助记词` 原始熵显示修复
- 固件 smoke、桌面模拟、真实 UI 截图和模块导入检查

## 5. 当前 `main` / `HEAD` 是什么

`main` / `HEAD` 是滚动开发线。

现在默认 clean 固件入口已经直接跟随 `HEAD`，所以：

- 想编当前 clean 固件，看 `firmware-clean -> HEAD`
- 想看仓库里当前已经保留的固件基线，看 `current-head-clean`
- 想追历史 `20260410b` 公开固件，再看 `offline-signer-clean-source-20260410b`
