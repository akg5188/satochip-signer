## 3. 当前树莓派构建规则

统一用：

```bash
bash scripts/build_pi_firmware_from_snapshot.sh
bash scripts/check_release_artifacts.sh
```

当前规则：

- `system-update-latest` 只能由干净仓库 + `clean` 构建覆盖
- 测试包必须换别的 `DIST_IMG` 名字
- `no-clean` 只给测试，不给正式基线
- 当前仓库里的 `system-update-latest.build-info.txt` 已经是 clean 新格式，不再需要 legacy 警告

## 4. 安卓构建规则

### `app/`

```bash
bash scripts/build_tp_relay_apk.sh
```

说明：

- 可以没有 keystore
- 没有时会回退到 debug 签名

### `wallet/`

```bash
bash scripts/build_wallet_release.sh
```

说明：

- `release` 必须有 `wallet/keystore.properties`
- 没有会直接失败

## 5. `dist/` 里的东西怎么理解

当前仓库里要重点分清：

- `system-update-steel-restore-fix-test.*`
  当前仓库本地保留的功能测试固件
- GitHub Releases 当前公开下载文件名仍是 `system-update-seedkeeper-suite-test.*`
- `system-update-latest.*`
  当前 clean 正式基线
- `satochip-wallet-release.*`
  当前保留的钱包 APK 及校验，不代表一定已经跟当前 `main` 对齐重编

`tp-qr-relay-android-latest.apk` 默认按需构建，不保证长期常驻 `dist/`。

以后判断 APK 是不是最新重编，不要只看文件名。

一定先看：

- `dist/*.build-info.txt` 里的 `repo_head`
- `build_script`
- `build_time_utc`

当前 `check_release_artifacts.sh` 也会对可选 APK 给出额外警告：

- 如果 `repo_head` 不是当前 `HEAD`
- 如果 `build_script` 不是标准入口脚本

## 6. 提交顺序建议

每次发布型改动建议拆成两步：

1. 先提源码和文档
2. 再提 `dist/` 产物

这样以后更容易看清：

- 哪个源码提交产出了哪张固件或 APK
- 哪个提交只是把产物回填进仓库

## 7. 每次发版前至少检查什么

```bash
git status
```

重点别把这些无脑带进去：

- `logs/`
- `local.properties`
- `wallet/local.properties`
- `seedsigner-os/output/`
- `seedsigner-os/buildroot_dl/`

## 8. 文档也要同步更新

现在文档已经按当前源码重写，后续再改功能时，至少同步检查：

- `README.md`
- `docs/快速开始.zh-CN.md`
- `docs/离线签名器使用教程.zh-CN.md`
- `app/README.md`
- `wallet/README.md`

不要再出现“代码变了，教程还停在旧架构”的情况。
